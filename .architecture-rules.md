# Architecture & Code Compliance Rules — HTML Website

These rules apply to all HTML, CSS, and JavaScript changes in this
repository. ArchBot checks every pull request against them.

## Markup & Semantics

1. **Use semantic HTML elements over generic `<div>`/`<span>`.** Use
   `<nav>`, `<header>`, `<main>`, `<footer>`, `<section>`, `<article>`,
   and `<button>` where they apply. A `<div onclick="...">` styled to look
   like a button must be an actual `<button>`.
2. **Every `<img>` must have an `alt` attribute.** Use a meaningful
   description for informative images, and `alt=""` (empty, not omitted)
   for purely decorative ones.
3. **Every form input must have an associated `<label>`,** either via
   `for`/`id` or by wrapping the input. Placeholder text alone is not a
   label.
4. **Heading levels must not skip** (e.g. an `<h2>` must not jump straight
   to `<h4>`). Headings must reflect actual document structure, not be
   chosen for font size.
5. **No empty links or buttons** (`<a href="#">` or `<button>` with no
   text content and no `aria-label`) — these are unusable for
   screen-reader and keyboard users.

## Accessibility

6. **Interactive elements must be keyboard-operable.** Anything with a
   click handler must also work via keyboard (native `<button>`/`<a>`
   elements get this for free; custom interactive `<div>`s need
   `tabindex`, a `role`, and key event handling).
7. **Color must not be the only way information is conveyed** (e.g. "red
   text means required" must also have a text label or icon, for
   colorblind and low-vision users).
8. **Don't remove focus outlines** (`outline: none` or
   `outline: 0` on `:focus`) without providing a clearly visible
   replacement via `:focus-visible`.

## CSS

9. **No inline `style="..."` attributes** for anything beyond a
   genuinely dynamic, JS-computed value (e.g. a progress bar width set at
   runtime). Static styling belongs in a stylesheet.
10. **No `!important`** except as a last-resort override of third-party
    CSS you don't control. Flag any new use for a comment explaining why.
11. **Use CSS custom properties (variables) for colors, spacing, and
    fonts** rather than repeating literal hex/px values across multiple
    rules — this file's own site uses `:root { --bg: ...; --accent: ...; }`
    as the pattern to follow.
12. **Avoid deeply nested or over-specific selectors**
    (e.g. `div#main ul.list li.item a.link span`). Prefer a single class
    on the target element.

## JavaScript

13. **No inline event handler attributes** (`onclick="..."`,
    `onload="..."`, etc., written directly in HTML markup). Attach event
    listeners in JavaScript via `addEventListener`.
14. **No `eval()`, `new Function(...)` from strings, or `innerHTML`
    assignment of unsanitized/user-provided content** — these are XSS
    risks. Use `textContent` for plain text, and a sanitizer for any HTML
    that must be inserted dynamically.
15. **No hardcoded API keys, tokens, or secrets in client-side JavaScript.**
    Anything shipped to the browser is public; secrets belong server-side.
16. **Avoid global variables.** Wrap page scripts in a module, an IIFE, or
    use `type="module"` — don't leak variables onto `window` unless
    that's the specific, intentional integration point.

## Performance & Loading

17. **Images must specify `width` and `height` attributes** (even if CSS
    also constrains their final size) to prevent layout shift while the
    page loads.
18. **Non-critical `<script>` tags must use `defer` or `async`**, not
    block rendering by loading synchronously in `<head>`.
19. **No render-blocking third-party fonts/scripts without `preconnect`**
    for their origin, if used on a first-paint-critical path.

## General

20. **No commented-out blocks of dead code** left in committed HTML/CSS/JS
    — delete it; version control already preserves the history.
21. **No `console.log` debugging statements** left in committed
    JavaScript.
